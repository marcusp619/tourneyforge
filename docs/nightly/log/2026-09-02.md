### Found: task 1's Verify block orphans the API server

Reproduced twice. The block does:
```bash
cd packages/api && bun run src/index.ts & API_PID=$!
trap 'kill "$API_PID" 2>/dev/null; rm -rf "$W"' EXIT
```
`&` binds to the whole `cd ... && bun ...` list, so `$!` is the **subshell's** pid, not
bun's. The trap kills the subshell and leaves bun holding `:3001`. After both runs,
`ss -ltnp` showed a live `bun` on 3001 and the next run would hit EADDRINUSE. The block's
own comment warns about exactly this hazard while the code commits it. Not fixed — that
is a Verify-block change and needs approval.

### The Verify block contains a contradiction. Measured, not argued.

Task 2's Deliver says dev:up must "start docker services". Its Verify says:
```bash
timeout 60 docker compose stop postgres
timeout 180 pnpm dev:up && fail "dev:up succeeded with postgres down — it is not checking health"
```
A script that starts docker services simply restarts the stopped postgres. Proven
directly, before writing any of the script:
```
docker compose stop postgres           ->  postgres not running
docker compose up -d --wait postgres … ->  exit=0, postgres running
```
and again in the real run, from the block's own output:
```
Container tourneyforge-postgres-1 Starting
Container tourneyforge-postgres-1 Started
Container tourneyforge-postgres-1 Healthy
  services healthy
FAIL: dev:up succeeded with postgres down — it is not checking health
```
These two requirements cannot both hold. **I did not weaken the block** — it stands
unchanged and task 2 is reported partial rather than done.

**Proposed replacement, for human approval only — NOT adopted:** keep the warm-start
timing check, which does genuinely distinguish polling from sleeping (2s measured), and
replace the dead-postgres case with a dependency the script cannot auto-heal — e.g. point
`DATABASE_URL` at a closed port and assert dev:up fails within the deadline. The intent of
the original (catch a script that sleeps instead of polling) is preserved; the mechanism
is one that a service-starting script can actually fail.

### Found and fixed while building: three process-handling bugs, all mine

- Log path was relative and resolved against the caller's cwd, not the target dir,
  because the `cd` happens in the backgrounded subshell.
- `$!` captured setsid's pid, not the server's — the same defect as task 1's block. Now
  the pid is read back from `ss` by port.
- **The script did not return.** Backgrounded children inherited this script's stdout, so
  they held the write end of the pipe and `pnpm dev:up | tail` blocked forever even though
  every server was up and healthy. Fixed with `</dev/null` and both streams redirected.
  This one cost the most time and is the most reusable lesson in tonight's log.
